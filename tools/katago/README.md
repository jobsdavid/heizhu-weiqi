# 围棋 AI 工具链

端侧围棋 AI 的**数据生成 → 训练 → 评测**链路。App 本体在仓库根目录
（`core/` 规则与搜索引擎、`app/` 电视端界面、`bench/` 对局评测台、
`app/src/main/assets/net/` 端侧权重）。

这里的脚本解决一个具体问题：**在算力受限的电视盒子上，如何得到一个"棋力可信、
难度真实递增、黑白公平"的围棋 AI，并且每一步都能用数据证明。**

---

## 1. 流水线

```
        ┌─────────────────┐
        │  KataGo (参考)   │  超人类引擎，只用于"出题"与"判分"，不参与端侧推理
        └────────┬────────┘
                 │ 自战对局
                 ▼
  ①  语料生成  distill_gen.py       取局面 → 标注策略分布 / 目差 / 行棋方
                 │                  （丢弃 |目差| > 15 的已分胜负局面）
                 ▼
  ②  训练导出  train_pv.py          3 平面输入 + 策略头 + 价值头，导出为
                 │                  纯前向可手写实现的 .bin + .json manifest
                 ▼
  ③  评测      posloss.py           配对位置级：单手期望目损、崩盘率（主判据）
              app_baseline.py       产品口径整局：胜率、黑白公平、健康度
              accept_sim.py         整盘棋回放 + 棋谱 + 规则级诊断
                 │
                 ▼
  ④  集成      app/src/main/assets/net/pv{9,13}-{tier}.bin/.json
```

端侧不用 ONNX / TFLite：网络很小（64–96 通道 × 5 残差块），纯 Kotlin 手写前向即可，
少一个运行时依赖就少一类设备兼容问题。

## 2. 快速开始

```bash
# 依赖（本仓库不含，体积原因）
pip install numpy torch
# KataGo：https://github.com/lightvector/KataGo/releases
# 模型  ：https://katagotraining.org          （本项目用 b18c384nbt）
#   放到 ./katago 与 ./nets/<model>.bin.gz

export PYTHONPATH=<repo>/tools/ml/pylibs
export LD_LIBRARY_PATH=/usr/lib/wsl/lib:<repo>/tools/katago/cuda-libs/nvidia/cudnn/lib

# ① 生成语料（13 路、50 局、每手取一个局面）
python3 distill_gen.py --size 13 --games 50 --plies 300 --every 1 --visits 300 \
    --max-lead 15 --proposer katago --out distill-13.jsonl

# ② 训练并导出（96 通道 × 5 块，8 个 epoch）
python3 train_pv.py --data distill-13.jsonl --out pv13 --size 13 \
    --width 96 --blocks 5 --steps 3312

# ③ 评测
python3 posloss.py      --size 13 --data distill-13.jsonl --positions 150 --visits 300 \
    --tier beginner --config old:旧.bin --config new:pv13.bin
python3 app_baseline.py 13 entry entry 80 400 pv13.bin pv13.bin
python3 accept_sim.py   record --size 13 --all-tiers

# ④ 集成到 App
cp pv13.bin pv13.json ../src/WeiqiTV/app/src/main/assets/net/   # 文件名对应档位 id
```

> 大物件一律不入库：语料 `*.jsonl`（316 MB）、权重 `*.bin/*.pt`（384 MB）、
> KataGo 二进制与官方网络（147 MB）、CUDA 运行库（2.2 GB）。

## 3. 组件

| 脚本 | 职责 |
|---|---|
| `distill_gen.py` | 生成语料。`--proposer katago` 让 KataGo 自己下并从它的对局取局面；`--max-lead` 过滤废局面；每条样本带 `gameId`（供训练按局划分） |
| `train_pv.py` | 训练并导出端侧权重。支持两种输入视角（见 §4.5）、按「局」分组划分训练/验证、导出 manifest（含 `view` / `k_value` / 层形状） |
| `posloss.py` | **主判据**。在**同一批干净局面**上配对比较多个网络/配置：平均/截尾/中位丢目、单手丢目 >10 目的占比（崩盘率）、分段（开局/中盘/官子）、按执色拆分 |
| `app_baseline.py` | 产品口径整局对局：复用产品 `GameState` 的真实终局判定，输出黑白胜率、摆烂局/被吃光局/未终局/非法手比例 |
| `accept_sim.py` | 按产品配置（档位 + 该档让子数）打**整盘棋**并打印棋谱；输出规则级诊断（填真眼、停手后仍在下等） |
| `grade.py` | 用 KataGo 逐手判分（旧口径，已不用于主判据，保留作交叉检查） |
| `bench/`（Kotlin） | 评测台。`appmatch` 打完整对局，`genmove` 给局面要一手；含 `drunkard`（随机+吃子）与 `beginner-proxy`（规则化初学者）两个对照代理 |

## 4. 评测方法论

这一节是本项目**返工最多**的地方，也是最有价值的部分：**先修量尺，再下结论。**

### 4.1 先做功效分析

用对局胜率当判据时 `Δp = 1/√n`：

| 要分辨的差距 | 所需局数/档 |
|---|---|
| 20 个百分点 | ≈ 50 |
| 10 个百分点 | ≈ 200 |
| 5 个百分点 | ≈ 780 |

`n=40` 的功效下限约 **110 ELO**。因此：

- 在 30–40 局上看到「非单调」，几乎总是**测不到**，不是「该轴无效」；
- 反过来，32 局的「白方 62%」也不构成偏色证据（Wilson 区间 `[0.45, 0.77]` 含 50%）。

**两个方向都要看区间**，否则会同时犯两类错误。

### 4.2 训练/验证按「局」分组，不按样本

局面是从同一局按手数切出来的，相邻两个只差一手棋、余弦相似度 ≈0.99。
按样本随机划分时，验证样本的「同局近邻」落在训练集的概率：

```
1 − (1 − val_frac)^m ，m = 每局样本数 ≈ 68  ⇒  ≈ 97%
```

⇒ 验证指标测的是**插值能力**，与泛化无关。本项目曾出现「top1 单调漂亮、
真实棋力不单调」的矛盾，根因就在这里。

### 4.3 有效样本量是「局数」

组内相关 ρ 下 `n_eff = n / (1 + (m−1)ρ)`：4099 条样本、每局 68 个 ⇒ `n_eff ≈ 119`。
把采样密度从「每 2 手」提到「每 1 手」只增加冗余；唯一能提高 `n_eff` 的是**局数**。

### 4.4 评测局面不能取自「自己的引擎自战」

自己的引擎会崩（大块被提、边界未定），那些局面本身含崩局。同一网络两种取样口径：

| 局面来源 | 官子段每手丢目 |
|---|---|
| 自己引擎自战 | 20.0 目 |
| KataGo 自战（干净、\|目差\|≤15） | 4.8 目 |

⇒ 指标方差会被局面难度主导，掩盖配置差异。因此评测统一用
`distill_gen.py --proposer katago` 产出的局面，并**同批配对**比较（配对把局面难度差掉，
方差只剩「配置 × 局面」的交互项）。

### 4.5 颜色对称：相对视角是数学保证

输入编码有两种，**不可混用**（权重按各自编码训练，manifest 的 `view` 字段驱动端侧推理）：

| 编码 | 平面 | 颜色对称性 |
|---|---|---|
| `relative` | [我方子, 对方子, 恒 1] | 网络在结构上无法区分黑白 ⇒ **数学保证** |
| `absolute` | [黑子, 白子, 是否轮到黑] | 必须配「必然换色」数据增强，否则会学出偏袒某色 |

实测：用 `absolute` 且换色增强被漏掉时，同网络自战黑方 20/32 = 62%（偏色）；
改用 `relative` 后回到 50% 附近。**端侧推理与训练侧必须逐字对齐，错配会让输出全错。**

### 4.6 难度参数有顺序依赖：先标贴目，再标让子

判胜门槛是 `黑净胜 > 2×komi`。贴目偏大时黑方永远跨不过门槛 ⇒ **整个让子阶梯被压平**：

```
9 路 · komi 3.75 · 每档 80 局（受让方 = 白）
  n=0 → 72%   n=1 → 78%   n=2 → 72%   n=3 → 75%   n=4 → 76%
  ⇒ 「让 0 子」与「让 4 子」胜率完全相同
```

改成 komi 1.25（先扫出的平衡点）后，n=0 回到 51/49，阶梯才能展开。
**顺序反了或功效不够，标定会静默失效，而「看起来有数据」是最危险的假象。**

## 5. 实测结论（可复现）

### 5.1 质量杠杆的性价比

单变量、配对位置级（147 个干净局面）：

| 变量 | 变化 | 平均丢目 | 崩盘率(>10目) | 配对差 95% CI | 判定 |
|---|---|---|---|---|---|
| 数据量 | 6.9k → 13.6k 条 | 5.00 → 3.78 | 16% → 11% | −1.02 [−2.65, +0.88] | 方向有效，未达显著 |
| 数据量 | 13.6k → 26.5k 条 | 3.78 → 4.32 | 11% → 14% | +0.54 [−1.15, +1.89] | **已饱和** |
| 容量 | 64×5 → 64×8 | 4.14 → 2.92 | 13% → 8% | −1.22 [−2.29, −0.18] | **显著** |
| 容量 | 64×5 → 96×5 | 4.14 → 2.29 | 13% → 4% | −1.85 [−3.30, −0.12] | **显著** |
| 搜索深度 | 1 层 → 2 层前瞻 | 2.41 → 3.63 | 6% → 8% | — | **越搜越差** |

结论：**容量 > 数据（会饱和） > 搜索**。

搜索变差有明确机理：网络是从 KataGo 蒸馏而来，**策略头本身就很准**；
用不可靠的价值头做两层前瞻，等于用弱估值去覆盖强的策略先验。

### 5.2 终局分布（9 路，同网同预算，n=80）

| komi | 黑方胜率 |
|---|---|
| 0.00 | 54% |
| 0.75 | 51% |
| 1.50 | 48% |
| 2.25 | 49% |
| 3.00 | 32% |

⇒ 平衡点 ≈ 1.25 子（13 路同理测得 3.75 已合适，n=120 时黑 48%）。

### 5.3 让子阶梯

13 路（n=120/档，受让方胜率）：`52% → 54% → — → 72% → 78%`，单调，每颗子约 **+6.5 个百分点**。

缺点是相邻档差（5–10 pp）小于 `n=80` 的噪声（SE ≈ 6 pp），
要确立「档距等分」需要 ≈ 400 局/档 —— 这一点如实留在文档里，不用噪声改参数。

## 6. 已知限制

- **规则实现只有简单劫**，没有超级劫；也没有「终局确认死子后提掉再数子」这一步。
  引擎靠「继续下、把死子提掉」逼近正确结果，而弱网络提不掉 ⇒ 终局数子会把未提的
  死棋算作其方地盘 ⇒ 偶发 ±100 目量级的净胜。这是当前棋力天花板的主要来源。
- 端侧网络只输出策略与目差，不输出归属（ownership），所以无法在端侧做死子判定。
- 引擎在胜负已定时不会「收手」，会下到「无单官」或手数兜底（点数 × 1.6）。
- 容量提升会增加端侧前向耗时（13 路·入门实测响应 ≈3 秒），
  低档的响应时间与「低档=快」的产品设定存在张力。

## 7. 工程约定

- **训练**必须 `unset LD_LIBRARY_PATH`（设了 cudnn 反而崩）；**评测/推理**必须设上。
- 不要用 `pgrep -f` 判断「前一个任务是否结束」：`bash -c` 的正文明文里含要匹配的字符串，
  会匹配到自身而死锁。用 PID 判活（`while kill -0 $PID`）。
- 批量脚本要把单局失败记成 `error` 并跳过，**否则一整档会白跑**（曾被清零 120 局）。
- 编码开关（`WEIQI_ABS_VIEW` / `WEIQI_RAW_VALUE` / `WEIQI_AUGMENT`）改动时，
  必须同步检查所有依赖该编码假设的地方：增强、导出、端侧推理。
