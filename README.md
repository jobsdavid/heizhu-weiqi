# 黑猪围棋（Heizhu Weiqi）

在电视上玩的围棋练习应用。**只用手里的遥控器**就能下完一整盘：方向键移光标、
OK 落子、返回键悔棋、菜单键更多。

面向的场景是「孩子在电视上学会下围棋、家长陪着下」。这个场景决定了两个真正的难点：

- **介质**：视距 2–3 米、只有 5 个方向键，界面必须一次看全、一次走到；
- **对手**：电视盒子算力有限，但 AI 必须**真的会下**——按规则下、难度真实递增、
  黑白公平，而不是随机摸子或靠"放水"制造深浅。

## 功能

- **人机对局**（单机单人），**9 路 / 13 路**可选
- **五档难度**（入门 / 初级 / 中级 / 高级 / 大师）。弱档的"弱"来自两处**可测量**的来源：
  **端侧网络强弱**与**思考预算 / 候选宽度**；**不靠"故意下错"放水**——
  引擎的每一个候选着法都是按自己的判断选出来的
- **完整围棋规则**：提子、打劫、禁自杀、眼、停一手、数子定胜负
- MCTS 会提子、避免一线爬、不填自己的眼、能判断「没有有用的一手」并停手收工
- **悔棋**：菜单里直接悔；返回键悔棋会先弹确认框（防误碰把刚下的一手撤掉）
- **提子在棋盘上可见**：光标环、最后一手标记、提子动画与音效
- **历史战绩**：按难度 / 时间 / 棋盘尺寸统计，含胜率与提子数
- **认输**：认输即终局，不数子（围棋里认输不结算）
- 音效与落子振动可分别开关，设置会被记住
- 全程离线，**不申请任何网络权限**

## 架构

```
core/   纯 Kotlin，无 Android 依赖。规则引擎 + MCTS AI + 端侧网络前向，可独立跑测试
bench/  纯 JVM 命令行「棋力评测台」：stdin 收局面 → stdout 回一手（JSON 行协议），
        Python 侧据此驱动本引擎与 KataGo 互殴、打分。刻意不做 GTP 协议 ——
        评测只需要「给局面、要一手」这一件事，多一套协议只会多一个与棋力无关的失败点
app/    Compose for TV 界面、本地 JSON 存档、音效
tools/  训练与评测链路（数据生成 / 训练导出 / 配对位置级测量 / 整盘棋验收）
```

`core` 不依赖 Android 是刻意的：规则与 AI 的正确性靠单元测试保证，不需要装机就能验证
——围棋逻辑出错的代价太高，不能靠「看起来下得挺像」来判断。

| 关键实现 | 位置 |
| --- | --- |
| 棋盘与合法着法（提子 / 打劫 / 自杀） | `core/.../rules/Board.kt` |
| 数子 | `core/.../rules/Scorer.kt` |
| MCTS 搜索与难度分档 | `core/.../ai/MctsEngine.kt`、`Difficulty.kt` |
| 着法评分（位置价值、一线惩罚） | `core/.../ai/PlayoutPolicy.kt` |
| 端侧网络前向（策略 + 价值） | `core/.../ai/PolicyValueNet.kt` |
| 权重装配与缺失回退 | `app/.../data/NetAssets.kt` |
| 电视端焦点与按键处理 | `app/.../ui/components/TvComponents.kt` |
| 棋盘绘制与提子动画 | `app/.../ui/game/BoardCanvas.kt` |

## 难度阶梯

每一档由三件事共同决定：**端侧网络强弱**（容量与训练量）、**候选宽度**（`netTopK`）、**思考预算**。

| 档位 | 预算 | 候选 | 网络 | 说明 |
| --- | --- | --- | --- | --- |
| 入门 | 300 ms | 6 | 最小 | 只留最像样的几个点，不做两层前瞻 |
| 初级 | 600 ms | 8 | 小 | |
| 中级 | 1.2 s | 10 | 中 | 起用两层前瞻 |
| 高级 | 2.0 s | 16 | 大 | |
| 大师 | 15 s | 24 | 最大 | 候选最全、算得最久 |

两条设计口径：

1. **弱档的"弱"必须来自"想得少"，不能来自"故意下错"**。项目明确排除了随机温度与
   失误注入（`temperature` / `blunderRate` 归零）——那类做法让棋形扭曲，看起来像"坏了"
   而不是"弱了"。低档只做两件事：少留候选、少做前瞻。
2. **网络强弱只提供"组"级别的差异**。配对位置级测量显示，五档网络可验证的差距是
   `{入门, 初级, 中级} ≈ 6.5 目/手` 与 `{高级, 大师} ≈ 5.4 目/手`（差 −1.54，
   CI [−2.68, −0.40] 显著），组内差异测不出来。方法与数据见
   [tools/katago/README.md](tools/katago/README.md)。

**已知限制（写在明处）**：AI 的**棋力地板偏高**。实测对照——用一个"知道规则但不做
形势判断"的代理去打，五档全部落败（9 路 0–22%、13 路 0%）；把让子加到 9 颗、候选降到
1 个、乃至关掉网络走随机 rollout，代理仍然赢不了。原因是端侧网络由 KataGo 蒸馏而来，
它的每一手都"像样"。⇒ 档位差距对**完全不会下棋的初学者**可能不可见，
真实校准点只能来自玩家反馈。

贴目（每档共用，按尺寸取值）：9 路 1.25 子、13 路 3.75 子，均为实测平衡点
（同网同预算、每点 80 局，黑方胜率 ≈50%）。

## 评测与标定

AI 的棋力用三层测量，全部脚本与实测数据在 **[tools/katago/](tools/katago/README.md)**：

| 层次 | 工具 | 看什么 |
| --- | --- | --- |
| 位置级（主判据） | `posloss.py` | 同一批干净局面上的**配对**期望目损、单手丢目 >10 目的占比（崩盘率） |
| 对局级 | `app_baseline.py` | 产品口径整局：黑白胜率、摆烂 / 被吃光 / 未终局 / 非法手比例 |
| 验收级 | `accept_sim.py` | 按产品配置打整盘棋并打印棋谱，含规则级诊断（填真眼、停手后仍在下等） |

有三条口径是踩出来的，写在工具链文档里也写在这里，因为它们比脚本本身重要：

1. **先做功效分析再下结论**。用胜率当判据时分辨率 `Δp = 1/√n`：分辨 10 个百分点需要
   ≈200 局/档，5 个百分点需要 ≈780 局。30–40 局上看到"非单调"，几乎总是**测不到**。
2. **训练/验证按「局」划分**。同一局切出的相邻局面余弦相似度 ≈0.99，
   按样本随机划分会让 ≈97% 的验证样本在训练集里有"同局近邻" ⇒ 验证指标测的是记忆。
3. **标任何难度旋钮之前，先标贴目**。判胜门槛是 `黑净胜 > 2×贴目`：贴目偏大 ⇒
   黑方必须多赢更多子才算赢，胜率被贴目压平。实测 9 路贴目 3.75 子时白方 65%（n=40），
   改成 1.25 子后回到 50%。贴目没标对时测其他旋钮，测到的都是贴目的效应。

## 构建

需要 **JDK 17**、**Android SDK（compileSdk 37）**、**Gradle 9.8**（AGP 9 要求 Gradle 9.x）。
本仓库不附 gradle wrapper，用本机 gradle 即可。

```bash
# local.properties 里写本机 SDK 路径
echo "sdk.dir=/path/to/Android/Sdk" > local.properties

gradle :app:assembleRelease
# 产物：app/build/outputs/apk/release/app-release.apk
```

安装到电视（电视需开启 ADB 调试）：

```bash
adb connect <电视IP>:5555
adb install -r app/build/outputs/apk/release/app-release.apk
```

APK 同时声明普通 `LAUNCHER` 与 `LEANBACK_LAUNCHER` 两个入口——小米电视的「应用」列表
枚举的是普通 LAUNCHER，只声明 Leanback 会找不到应用。

## 测试

```bash
gradle :core:test                # 规则 + 引擎 + 网络前向：84 个用例
gradle :app:testDebugUnitTest    # 界面布局 + 焦点 + 权重装配：38 个用例（Robolectric + Compose）
```

规则部分用**朴素参考实现做差分比对**（`GoRulesConformanceTest`）：另写一份慢但一眼能看懂
的规则实现，在随机对局中逐步比对提子结果、气数、终局比分。两份实现同时错在同一处的概率，
远低于一份实现悄悄写错。

界面部分（`TvScreenLayoutTest`）在无头环境渲染 9 个页面，检查有没有元素被压扁、有没有布局
重叠、每个页面能不能用方向键走到该走的地方。它抓到过真机上肉眼很难发现的问题：
历史页 5 行分组时最后一行被压成 0 像素。

## 头像：仓库里是占位图

`app/src/main/res/drawable-nodpi/avatar_*.png` 是**生成的卡通占位图**，不是真人照片
——开源仓库里不该有别人的家人照片。

想换成自己的图：把图片放到仓库外的任意目录，结构如下

```
<你的目录>/drawable-nodpi/avatar_boss.png      # 左侧，对手
<你的目录>/drawable-nodpi/avatar_warrior.png   # 右侧，自己
```

然后在 `local.properties`（该文件不进版本控制）里指向**这个目录的父目录**：

```properties
avatars.dir=/absolute/path/to/<你的目录>
```

构建时会用 buildType 的 source set 覆盖 `main`，你的图优先于仓库里的占位图；
不配置就用占位图。配错了（比如指到了 `drawable-nodpi` 本身）会在构建日志里出声提示，
而不是静默地继续用占位图。

## 已知边界

- **算力是硬约束**。网络前向跑在电视 CPU 上（纯 Kotlin 手写卷积）：实测单次前向
  32×2 约 38 ms、64×4 约 236 ms、64×6 约 356 ms，13 路同架构再慢约 2.1 倍
  （与棋盘点数成正比，169/81）。一次选点的代价是 `候选数 ×（1 + 应手数）` 次前向，
  所以每手等多久由网络大小与档位共同决定。当前 13 路用 96×5 的权重换取显著的棋力
  （单手丢目 4.14 → 2.29、崩盘率 13% → 4%，配对测量 CI 排除 0），
  代价是 13 路·入门档实测响应约 3 秒。
- 网络是**可选资源包**：某尺寸/档位缺权重就回退到无网络的随机 rollout 路径，
  功能降级但不崩；缺失会被记住，不会每次开局都去读一遍 assets。
- **数子不判死子**：采用「只接触单色的空区归该色」的算法，盘上仍有气的死棋会算成活的；
  也不是严格的中国规则数子。正常局面偏差很小，极端局面（大片未定）会失真——
  由于引擎在胜负已定时不会"收手"，这类失真偶有发生（偶发 ±100 目量级的净胜）。
  端侧网络只输出策略与目差，不输出归属（ownership），无法在端侧做死子判定。
- 规则实现只有**简单劫**，没有超级劫。
- 提子动画是两段：**闪 1 秒 → 淡出 1 秒**。
